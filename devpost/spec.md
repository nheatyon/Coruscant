## How This Works, In Plain Language

Coruscant runs on this Mac as one local application server. React draws the browser interface; freshly written CSS carries the exact Coruscant console design. Fastify receives browser requests, checks the selected demonstration context and applies permitted actions. SQLite keeps the authoritative records in a file on the Mac. Three.js draws the Earth and either C13's same-ID real predictions or the explicitly separate demonstration context. C13 locally computes bounded sampled center-point LOS plus the approved applicable evidence, nominal-center proximity and illumination checks. C14 presents and explicitly saves tentative technical plans. These checks do not establish whole-area imageability, actual collection availability or workflow status.

A request has one identity from its first explicit Planning save or direct submission onward. Saving Planning does not submit it; later explicit submission retains that identity/reference and freezes actual submitted actor/contact/time. Customer Requests, Mission Control, the staff workbench and SatSuite read that same request and linked records. A selected tentative plan has immutable versions; a saved quote names the brief revision it prices; acceptance fixes that quote, brief and selected-plan version or No selected plan; the initial staff schedule names that acceptance. A result names the same request, exact image versions and reviewed finding. A point note names its image version and author.

Each consequential action is a short transaction: either all of its record changes, history and retry receipt are saved, or none are. A transaction is a group of database changes saved together. The browser supplies the version it reviewed; the server refuses an obsolete version rather than overwriting newer work. An unchanged retry can retrieve the earlier successful outcome after a lost response, without applying the action again. Current permission is checked even when retrieving that outcome.

The browser holds an opaque cookie: a random session identifier, not an actor's role. The server resolves it to a fixed demonstration persona, permitted audience and workspace, and checks present membership and authority on every protected read or write. This demonstrates enforced application decisions within a simulation. Anyone with access to the local app can deliberately choose its sample personas. It does not authenticate a real person, protect against the person controlling the computer or make publicly committed synthetic source art secret. It must not become a publicly hosted access system.

Material publication, organization entitlement and delivery are three separate actions. A private image never becomes readable merely because a button is hidden or its identifier is obscure. The same server checks image/thumbnail responses as well as result metadata. Delivery is a separate staff command, enabled only when the complete published pair and reviewed published finding are currently readable by the intended organization under valid rights.

#### Delivery: authorization and receipt before file preflight

A new delivery requires Scheduled, the accepted request/schedule/result association, a previewed1–4000-character customer note, Aligned dates under the decision above and complete current intended-customer readability. A replay recovers a committed historical outcome; it is not a new readiness decision. Use this combined order:

1. **Initial short database gate.** Validate envelope/Host/Origin/CSRF, opaque session and current context. In a short transaction check active Staff Admin authority, current audience/context generation and authorization for the parent request, then look up the globally unique bound receipt. These authority checks do not require Scheduled status or readable result files. An unchanged authorized receipt returns its original permitted saved IDs/committed versions/historical delivery fact immediately, before expected-version/token-expiry/status/date/publication/rights/file-readiness guards. Reused key with changed binding/payload conflicts. No file is opened and no bytes/current-access grant is returned through the receipt.
2. **Only a new attempt preflights files.** If no receipt exists, release the transaction; resolve the candidate exact required pair/versions/hashes. Read and hash bounded private files under the protected-root containment/type rules outside any write lock. Capture a version/hash proof or a safe failure; do not yet return a readiness failure that could mask an identical attempt committing concurrently. The app does not mutate/delete referenced published files. No transaction spans awaited I/O, computation or browser review.
3. **Final short transaction, even on preflight failure.** Begin IMMEDIATE; repeat current Staff Admin/session/context/parent authority, then receipt lookup. If an identical authorized attempt committed during preflight, return that saved success even if this preflight failed. Revoked authority/obsolete context still denies receipt disclosure. If no receipt exists, check current expected versions, unconsumed/unexpired matching confirmation, Scheduled state, accepted associations and all current readiness conditions. Require aligned comparison dates/current exact date-review snapshot, both exact images Published, current reviewed Published finding citing that pair, current matching organization/rights/entitlement and intended active customer membership. Compare database IDs/versions/hashes with the successful outside-lock proof. Changed versions or failed proof refuse the new action without delivery/event/receipt mutation; retain note/input. Perform no file work inside this transaction.
4. **Commit/return once.** Commit unique delivery, evaluated readiness/date-review facts, Delivered/version change, history, consumed confirmation and minimal successful receipt together. Return only after commit. A response or optional projection failure cannot erase saved success. A fresh key is a new command and cannot bypass current readiness, unique-delivery or status guards.

If receipt lookup/finalization itself is busy/unavailable, report retryable uncertainty with the same key retained, not a definitive claim that no attempt committed. Both success and failure preflight paths must pass the final authority/receipt gate before a new-action readiness error is returned. Historical Delivered can coexist with a subsequently withdrawn finding or unavailable file: new projections/bytes use current access, while an authorized unchanged retry recovers history without a second event. No receipt serves private bytes. No grant/publish/clock/external-delivery shortcut exists.

### Replay ordering and version checks

Develops [final review/submission](prd.md#prd-brief02-review-submit), [shared failure expectations](prd.md), and [MISSION-02](prd.md#mission-02). Use one logical action key for an unchanged attempt, retained through uncertain network outcomes. Fingerprint command, target, normalized complete payload, reviewed parent/child versions and context binding. Do not normalize away meaningful text/terms or treat an edited form as the same action.

For each guarded command, apply the sequence below. **Delivery additionally uses C08's initial authority/receipt gate before outside-lock file preflight, and repeats this sequence at finalization on both preflight success and failure.** Its readiness/file work never runs before the initial receipt check.

1. Resolve the opaque session and correct audience, then start the short write transaction. Read/check active actor, current session/membership/role/offer grant as appropriate, target ownership and expected active context/generation within that same transaction, before replay lookup. A removed grant/member or wrong workspace cannot recover a past receipt merely by knowing its key. Keep this synchronous section free of intervening asynchronous work.
2. Within the write transaction, inspect the globally unique action receipt. Same authorized binding and identical fingerprint returns the original successful outcome **before** rechecking consumed request version, confirmation expiry/consumption, current quote expiry/supersession, already-accepted/Delivered state or current material/date/file readiness. A committed acceptance replay after the former valid-until instant is still that original success; it is not a new expired acceptance. Return only currently permitted receipt facts, no new private material access.
3. A reused key with changed actor/audience/workspace/target/payload is a safe conflict, never another submission and never another actor's receipt/reference. Do not create a second record because a key is scoped only by actor. Reject obsolete context even if a matching receipt exists.
4. For a genuinely new action, validate a matching current unconsumed command-review token where required, current business state/expiry/required fields and expected aggregate/child versions. Conditional updates must affect exactly the intended row/version. Refuse stale work; preserve browser inputs for refresh/review.
5. Commit mutation, immutable history and successful receipt together. Roll back on failure; do not leave a success receipt for a failed operation. No awaits/external work or response precede commit. After commit, a response/refresh failure remains recoverable by that same action key.

This order is deliberate: running stale-version or expiry guards before receipt lookup would turn a successfully committed but response-lost command into a false failure. Current authorization/context must nevertheless precede replay. Changed form values generate a fresh action only after current-record review; blindly retrying a new key must not bypass the stale-state checks. Retain committed receipts durably with their parent records; in-memory-only deduplication would fail after process restart.

#### OMM normalization, physical calculation and display

Accept bounded JSON arrays from the allowlisted groups and validate every row independently against the canonical source schema. No one-object assumption or fixed C/D payload is permitted. Reject leap-second strings and invalid/nonfinite/decayed propagation. Let observer ECF point be O, satellite point S, line-of-sight v=S−O, and local geodetic up u=(cosφcosλ,cosφsinλ,sinφ). Elevation is atan2(v·u, sqrt(max(0,|v|²−(v·u)²))); slant range is |v|. Terrain, refraction, pointing, mode, full-circle imageability, weather, capacity and operator agreement remain unknown.

Physical calculations are independent of the existing spherical globe projection. Convert approximate ECF to WGS-84 geodetic latitude φ, east-positive longitude λ and height h in kilometres. Draw at `(1+h/6378.137) × (cosφcosλ, sinφ, −cosφsinλ)` using the same C04 texture/picking/target convention. Reject decayed/nonpositive-height or nonfinite positions. This is a declared geodetic spherical display projection, not the physical ECF vector; never feed it back into range/elevation calculation.
